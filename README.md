# 融e衡 A/B 实验网页

依据《融e衡项目Claude交接文档》V2.0（2026-09-19）实现。
目前包含**参与者端**、**计算引擎**、**管理员后台**和 **Supabase 初始化 SQL**。
还差最后一步：建 Supabase 项目并实现 `SupabaseBackend`，把数据从浏览器搬到集中数据库。

- 参与者端：`http://localhost:5173/`
- 管理员后台：`http://localhost:5173/#/admin`（默认口令 `rongeheng-dev`）

---

## 一 快速开始

需要 Node.js 18 以上（开发时使用 v24.19.0）。

```bash
cd rongeheng-ab
npm install
npm run dev      # 本地开发，浏览器打开终端里显示的地址
npm run test     # 计算 + 流程 + 视觉守卫 + 指标 + CSV + 管理端，共 90 条
npm run build    # 类型检查 + 生产构建
```

手机真机测试：`npm run dev` 已开启 `host: true`，用手机连同一个 Wi-Fi，
打开终端里 Network 一行的地址即可。

环境变量：复制 `.env.example` 为 `.env.local`。当前阶段不填任何值也能完整跑通，
默认使用浏览器本地存储。

## 二 目前能做什么，不能做什么

**已经实现**

- 知情同意 → 匿名码 → 基线问题 → 三个情境 → 完成页的完整参与者流程。
- A 版与 B 版两套界面，共用同一份情境参数和同一个计算模块。
- 三个情境顺序随机，顺序在会话开始时确定一次并写入会话记录。
- 刷新或关掉页面后，用同一个匿名码恢复到原进度，不会生成第二个参与者。
- 每个情境只能提交一次（`session_id + scenario_id` 幂等）。
- 记录决策、关键点击事件和耗时，字段名与交接文档第七章一致。
- 提交失败时停在原页并提示重试，不显示"已成功"。

- 管理员后台：总览、主要指标、原始记录筛选、参与者明细、CSV 导出、按匿名码撤回删除。
  入口是 `http://localhost:5173/#/admin`。
- Supabase 建表 SQL、索引、唯一约束、RLS 策略、参与者写入函数、匿名码导入脚本
  （`supabase/schema.sql` 与 `supabase/seed_access_codes.sql`，可直接粘进 SQL Editor 执行）。

**还没有实现**

- **数据没有集中保存。** 前端仍然写浏览器 localStorage，SQL 已经写好但还没有人建 Supabase 项目，
  `SupabaseBackend` 也还没写。这不满足交接文档"集中记录"的要求，**不能用于正式采集**。
- 因此匿名码的"一码一人"目前只在单台设备内生效，换一台手机用同一个码会被当成新参与者；
  管理员后台看到的也只是本机数据。
- 管理员登录目前是一道**本地开发闸门，不是访问控制**：口令在前端比对，
  绕过页面直接读 localStorage 就能拿到全部内容。真实权限由 Supabase 的管理员登录 + RLS 提供。

接入 Supabase 时，只需新增一个 `SupabaseBackend` 实现 `src/lib/storage.ts` 里的
`DataBackend` 接口，并在 `createBackend()` 中切换，页面代码不需要改动。

## 四 A 版与 B 版的差异

两版的商品、型号、售价、分期月供、选项集合、选项顺序、选项文案、按钮样式完全一致。
B 版只增加决策信息：

| | A 版 | B 版 |
| --- | --- | --- |
| 商品与售价 | ✔ | 完全相同 |
| 分期月供 | ✔ | 完全相同 |
| 情境资金设定 | 只给"可自由支配金额" | 相同，另加资金情况面板 |
| 未来 30 天必要支出、最低应急储备 | ✘ | ✔ |
| 选中后的「付款后剩余可用资金」摘要 | ✘ | ✔ |
| 付款后未来 30 天最低可用余额 | ✘ | ✔ |
| 分期总支付、利息与手续费 | ✘ | ✔ |
| 分期折合年化利率 | ✘ | ✔ |
| 每月固定负担 | ✘ | ✔ |
| 先储蓄后购买所需月数 | ✘ | ✔ |
| 替代项与原商品的价格差 | ✘ | ✔ |

选中某个选项后，两版都会在提交按钮上方回显「你当前的选择：X」——结构一致，
但只有 B 版在这块继续给出付款后剩余可用资金、最低余额和与应急储备的对比。
A 版恒定只有那一行选择回显，`flow.test.tsx` 里有一条测试把 A 版所有详情展开后逐词检查，
确保「付款后剩余可用资金」「折合年化利率」「应急储备」「必要支出」「总支付」一个都不出现。

**防诱导措施**：深色视觉系统里确实定义了语义色，但它们按【信息类型】分配，
不按【这个选择好不好】分配——同一个指标换任何选项看，颜色都不变，只有数值和条长在变：

| 颜色 | 用在哪 | 为什么不算诱导 |
| --- | --- | --- |
| 翡翠绿 `#2FBF9F` | 剩余可用资金 | 余额是正是负都是翡翠绿 |
| 琥珀金 `#E4B95E` | 年化利率、利息与手续费 | 任何分期都是琥珀金 |
| 绿 `#4BC79A` | 应急储备值、余额条上的储备刻度 | 它是固定阈值，与选择无关 |
| 柔和红 `#E57373` | **未启用** | 见下 |

唯一会随判定结果变色的是 `styles.css` 里的 `--verdict-risk-ink` / `--verdict-safe-ink`，
当前都指向主文字色，也就是"低于应急储备"和"不低于应急储备"长得一模一样。
要做产品演示版（非实验）时把这两行改成 `var(--risk)` / `var(--success)` 即可，
但**改了就不要拿这个版本跑正式实验**。`src/styles.test.ts` 会在改动后失败，用来提醒这件事。

此外：没有任何选项被设为默认选中，"暂不购买"排在最后且样式与其他选项一致，
风险表述为中性的"低于应急储备"，不出现"错误选择""冲动消费"之类的评价。

## 五 三个需要项目负责人确认的判断

交接文档在以下三处没有给出唯一答案，实现时做了确定性处理，**预试前请确认，确认后随版本冻结**。

### 5.1 A 版是否展示"低价替代项"这个选项

交接文档 4.2 表格写 A 版"低价替代：不展示"，同一节又要求"A/B 使用相同最终选择集合"，
而 `decisions.final_choice` 的取值里包含"低价替代"。这两条无法同时满足。

**当前处理**：两版都提供相同的 5 个选项（全款、分期、先储蓄后购买、低价替代、暂不购买），
顺序相同。A 版的替代项详情只给名称、价格和分期月供，与主商品同一信息层级；
B 版的替代项详情额外给出余额推演、总支付和与原商品的价格差。
这样 `clicked_lower_price` 在两版中含义一致（是否展开替代项详情），可以直接比较。

**另一种选择**：A 版彻底不出现替代项，选项集合变成 4 个，A/B 选项数不同，
`clicked_lower_price` 在 A 版恒为空。若选这条，需同时修改分析方案。

### 5.2 A 版看不看得到"可自由支配金额"

交接文档 4.2 写 A 版"现金流：不展示"。但如果 A 版参与者完全不知道自己有多少钱，
三个情境就没有预算可言（电脑情境售价 6000 高于可用资金 5000，全款选项会变成不可能的选择）。

**当前处理**：两版都在情境开头给出"假设你现在可自由支配 X 元"，这属于情境设定；
"未来 30 天必要支出""最低应急储备""付款后余额"三项仍然是 B 版独有。

### 5.3 低价替代项的分期参数

交接文档 4.3 只给了替代项的价格，没给分期期数和每期金额，但 4.4 要求
"低价替代项按其对应支付路径重新计算"。

**当前处理**：沿用原商品的分期费率 `installment_total / base_price`，期数相同，
在配置里标记 `alternative_installment_derived: true`。推导结果：

| 情境 | 替代项价格 | 期数 | 每期 | 总支付 |
| --- | ---: | ---: | ---: | ---: |
| 电脑 | 4999 | 12 | 458.24 | 5498.88 |
| 手机 | 3999 | 12 | 373.58 | 4482.96 |
| 培训课程 | 1999 | 6 | 346.61 | 2079.66 |

如果要改成整数月供，请直接改 `src/config/scenarios.ts` 并同步更新 `calc.test.ts` 的期望值。

另外，"先储蓄后购买所需月数"交接文档也未给公式，当前规则写在 `calc.ts` 的 `monthsToSave`：
每月可结余 = 可自由使用资金 − 未来 30 天必要支出 − 最低应急储备，
所需月数 = ceil(商品价格 ÷ 每月可结余)。三个情境分别为 8、3、8 个月。

## 六 计算与风险标签

全部集中在 `src/lib/calc.ts`，A 版 B 版共用，页面里没有第二份金额计算。

```
剩余可用资金 = 当前可自由使用资金 − 当期需支付金额
最低可用余额 = 当前可自由使用资金 − 未来 30 天必要支出 − 当期需支付金额
最低可用余额 < 最低应急储备  ⇒  high_risk_choice = true
```

"剩余可用资金"是付完款后手里还剩多少钱，"最低可用余额"再往下扣掉未来 30 天的必要支出。
风险标签只看后者，口径与交接文档 4.4 完全一致，没有因为新增前者而改变。

### 6.1 分期利率

情境参数里的每期金额和分期总支付本身就含利息（电脑 6000 → 6600，手机 4999 → 5604，
课程 2999 → 3120），但"总息费 600 元 / 本金 6000 元 = 10%"这个说法会让人严重低估成本：
分期是逐月还本的，真实占用的资金远小于本金全额。

`calc.ts` 的 `monthlyRate()` 用二分法反解等额本息方程

```
本金 = 每期金额 × (1 − (1 + i)^−期数) ÷ i
```

得到真实月利率，再按 `APR = i × 12` 的名义年化口径换算，与消费金融产品的披露方式一致。

| 情境 | 本金 | 分期 | 总息费 | 总息费÷本金 | **折合年化** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 电脑 | 6000 | 12 × 550 | 600 | 10.00% | **17.97%** |
| 手机 | 4999 | 12 × 467 | 605 | 12.10% | **21.63%** |
| 培训课程 | 2999 | 6 × 520 | 121 | 4.04% | **13.70%** |

替代项分期沿用同一费率推导，因此年化与原商品一致（测试里有断言锁定这一点）。
年化利率只在 B 版展示——它属于交接文档 4.2 划给 B 版的"成本信息"。

`npm run test` 覆盖三个情境 × 六条支付路径（全款、分期、先储蓄、替代项全款、替代项分期、暂不购买）
的当期支付额、最低可用余额和风险标签。期望值由交接文档参数手工推算，全部写死在测试里。
当前结果：

| 情境 | 全款 | 分期 | 先储蓄 | 替代全款 | 替代分期 | 暂不购买 |
| --- | --- | --- | --- | --- | --- | --- |
| 电脑 | 高风险 | 否 | 否 | 高风险 | 否 | 否 |
| 手机 | 高风险 | 否 | 否 | 高风险 | 否 | 否 |
| 培训课程 | 高风险 | **高风险** | 否 | 高风险 | 否 | 否 |

培训课程的分期首期后余额 680 元，低于 800 元的应急储备，因此同样标记高风险。
这是冻结参数带来的结果，不是 bug；如果不希望出现这种情况，请在预试前调整参数并重跑测试。

`src/flow.test.tsx` 另外用 jsdom 把参与者流程整体跑一遍，自动验证：三个情境提交后到达完成页、
同一匿名码只生成一条参与者记录、已完成的码不能再次作答、无效码不放行、
刷新后回到原进度而不是从头开始、A/B 两版选项集合与顺序完全相同、
完成页文本中不出现"A 版""B 版""对照组""实验组""假设""正确""冲动""错误"等字样。

当前 `npm run test` 结果：90 条全部通过（计算 31 + 参与者流程 9 + 样式守卫 6 + 指标 15 + CSV 13 + 管理端 16）。

## 七 匿名码

`src/config/accessCodes.ts` 里是 50 个码：`PILOT01`–`PILOT10`（预试，A/B 各 5）、
`A001`–`A020`、`B001`–`B020`（正式）。

页面通过**查表**得到分组，不解析编号字符串——接入数据库后把 `lookupCode` 换成后端安全函数即可。
参与者界面任何位置都不出现"A 版""B 版"或分组字样，匿名码错误提示也不透露该码属于哪一组、
是预试还是正式。

正式码在分发前应打乱顺序，按招募先后依次发放，避免研究人员主观挑选分组。
这一步属于线下流程，不在代码里。

## 八点五 管理员后台

入口 `#/admin`。五个标签页对应交接文档第八章：

| 标签页 | 内容 |
| --- | --- |
| 总览 | 已登记码、已开始、已完成、进行中、已撤回、正式/预试分别计数、A/B 完成数 |
| 主要指标 | A/B 两列并排：平均与中位高风险比例、四分位、平均高风险情境数、至少一次高风险人数、分期选择率、暂缓购买率、低价替代选择与点击率、改过选择比例、决策时间中位数、B 版模块查看率；下方给绝对差和分情境拆分 |
| 原始记录 | 决策级表格，可按正式/预试、A/B、完成情况、情境筛选。**只读** |
| 参与者明细 | 只有匿名码和匿名基线字段 |
| 导出与撤回 | 五张表一键导出 CSV；输入匿名码二次确认后删除全部关联记录 |

### 三条刻意的设计

**主要指标按参与者层面算。** 个人高风险比例 = 三个情境中高风险选择数 ÷ 3，
A/B 各自取这些比例的均值与中位数。40 人 × 3 情境是 120 条决策，但只有 40 个独立单位——
后台在页面上写明了分析集人数，避免把 120 条当成 120 个人（交接文档 10.3）。

**不做推断统计。** 后台只给描述性数字和点估计。置换检验、Mann-Whitney U、bootstrap 置信区间
属于采集结束、版本冻结之后一次性运行的分析脚本。采集期间能随时刷新 p 值，很容易变成
"看着数字决定什么时候停"或"挑一个好看的口径"，这正是交接文档 10.5 警告的事。

**缺失值显示「—」不显示 0。** 分母为 0 时指标返回 `null`，界面渲染成「—」。
未完成会话、撤回记录、没作答的基线字段在 CSV 里导出为空字符串，不是 `0` 也不是 `FALSE`
（交接文档 9.3）。

### CSV 导出

五张表：`participants`、`experiment_sessions`、`decisions`、`events`、`withdrawal_log`。
UTF-8 带 BOM（Excel 双击不乱码）、时间为 UTC ISO 8601、布尔统一 `TRUE`/`FALSE`、
CRLF 换行、`scenario_order` 用竖线分隔。四张核心表都带 `participant_id`，
后三张都带 `session_id`，导出后可直接关联。

### 撤回删除

输入匿名码 → 二次确认 → 物理删除参与者、会话、决策、事件 → 匿名码标记 `withdrawn`
→ 写一条只含匿名码与处理时间的日志。后台**没有任何修改参与者答案的入口**，
只能整体删除（交接文档 8.8）。

## 八点六 Supabase

`supabase/schema.sql` 和 `supabase/seed_access_codes.sql` 可以直接粘进
Supabase 控制台的 SQL Editor 执行，两个文件都可重复执行。

schema.sql 建七张表（access_codes / participants / experiment_sessions / scenario_config /
decisions / events / withdrawal_log）、索引、唯一约束、RLS 策略和参与者写入函数。
几个关键决定：

- **匿名码只存 sha256 哈希**，明文不入库；`access_codes` 没有面向参与者的 select 策略，
  前端一行都读不到，分组由数据库函数分配，前端无法解析编号自行判断。
- **参与者不能直接写任何表**，只能调用 `start_experiment` / `submit_decision` / `log_event`
  三个 SECURITY DEFINER 函数。情境顺序在服务端随机，风险标签由服务端按 4.4 的公式重算，
  不信任前端传来的值。
- **没有任何表有 update 策略**，管理员也改不了参与者答案。
- `submit_decision` 用 `on conflict (session_id, scenario_id) do nothing`，
  断网重试不会产生第二条记录。

seed 文件末尾有权限验收的三步，照着做能验证交接文档 7.8 的要求：
参与者只看得到自己那一行、查 `access_codes` 返回 0 行、管理员能读全部但 update 被拒。
